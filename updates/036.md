## Journey and Troubleshooting

### 1. Handling strict type checker warnings on ZodError property access
- **Problem**: The catch blocks in all controllers were attempting to fetch error messages using `err.errors[0]?.message`. The compiler threw errors stating `Property 'errors' does not exist on type 'ZodError<unknown>'`.
- **Analysis**: In TypeScript, the standard property representing parsed Zod validation issues on `z.ZodError` instances is `.issues`, not `.errors`.
- **Solution**: Replaced all references to `err.errors[0]?.message` with `err.issues[0]?.message`.

### 2. Matching Zod record key arguments
- **Problem**: Zod's `z.record(z.any())` invocation threw `Expected 2-3 arguments, but got 1` error.
- **Analysis**: The typescript typing of `z.record` in the local node environment expected the key schema explicitly.
- **Solution**: Changed the invocation to `z.record(z.string(), z.any())`.

### 3. Matching exact enums and service structures
- **Problem**: Passing strings where service functions expected exact union types (`"document" | "conversation" | "explicit" | "extracted"` or `KGNodeType`/`KGEdgeType`) caused assignment errors.
- **Analysis**: TypeScript requires types to be exactly matched. We needed to enforce these enums at the Zod schema parsing boundary.
- **Solution**: Defined `kgNodeTypeSchema` and `kgEdgeTypeSchema` as `z.enum` matching the types in `memory.types.ts`. Used them directly in the Zod schemas for edge and node upserts. Additionally, mapped parsed messages to include mock `id` and `timestamp` properties before passing them to the short-term memory conversation extractor service.
- **Result**: Codebase successfully compiles and type check passes monorepo-wide.
