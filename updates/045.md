# Update 045: Integration of Local SmolLM 135 SFT Model

Date: 2026-07-04

## Purpose
Enable the system to optionally run query generation locally using a fine-tuned SmolLM-135M model adapter located inside `/server/cpt_sec_adapter`, rather than calling the Google Gemini API. This allows for offline, low-resource query processing and localized model evaluation.

## Journey and Problem Approached
During research, importing PyTorch in the system Python environment failed due to missing Windows runtime components (`shm.dll` error). We identified a virtual environment under `apps/rag-pipeline/.venv` that successfully loaded PyTorch and Transformers. However, it lacked the `peft` module. When trying to use pip to install it, we discovered `pip` was missing from the virtualenv. We successfully bootstrapped `pip` using python's `ensurepip` and installed `peft` and `accelerate`.

Since loading a 135M parameter model from disk on every single network request would incur a 5-10 second loading latency, we decided to implement a background Python HTTP microserver inside the workspace. The server loads the model once and handles inferences sequentially over a REST endpoint.

---

Step 1: Bootstrapped virtualenv dependencies using `ensurepip` to install `pip`, then successfully installed `peft` and `accelerate`.  
Step 2: Implemented `run_smollm_server.py` using Python's built-in `http.server` to load the fine-tuned adapter on top of `HuggingFaceTB/SmolLM-135M-Instruct` base model and serve it over local port 5002.  
Step 3: Added automatic startup and SIGINT/SIGTERM cleanup hooks for the model server inside `apps/server/src/index.ts`.  
Step 4: Updated `chatSlice.ts` and `ChatContent.tsx` to display a premium Radix select dropdown in the chat header, updating the redux state and routing query requests with the selected `llm` payload.  
Step 5: Verified CPU generation via REST API and confirmed model loaded successfully and ran text generation on CPU in under 30 seconds.  
Step 6: Diagnosed and resolved Next.js SWC loading error (`not a valid Win32 application`) caused by disk space exhaustion (`ENOSPC`) on the C: drive. Freed up ~710 MB of space by purging Next.js and Turbo build caches, reinstalled the SWC binary successfully, and verified that both the frontend and backend servers compile and boot with no issues.  
Step 7: Diagnosed and resolved PyTorch Windows segmentation fault (STATUS_ACCESS_VIOLATION exit code `3221225477`) when launching from Git Bash/Mintty shell. Programmatically locked PyTorch CPU execution to 1 thread inside the Python server by calling `torch.set_num_threads(1)` and `torch.set_num_interop_threads(1)` right after import, stabilizing model loading in all environments.  
Step 8: Fixed generation looping bug (where the model repeated output turns indefinitely) by explicitly adding `<|im_end|>` to the generation stop/EOS token IDs list and applying a `repetition_penalty=1.2` parameter.
